05 · AI Agent 系统总览

6 个职责单一的 Sub-Agent

每个 Agent = 一段精心设计的 Prompt + 独立的温度与 token 上限,职责彻底解耦,可单独迭代、单独触发。

💬conversation

实时对话 + 触发决策。流式 SSE,温度 0.7,挂载 trigger_generation 工具。系统的大脑。

📋requirement

结构化需求分析文档 (Markdown)。温度 0.3,3000 tokens。

🏗design

系统架构图 (Mermaid TD)。读已有架构图增量演化。

🔗er

数据库 ER 图 (Mermaid erDiagram)。读已有 ER 图演化。

🔌api

RESTful API 规范文档。读已有 API spec 作为上下文。

🗓plan

开发路线图与里程碑。温度 0.3,4000 tokens。

◆
注意:没有独立的 orchestrator agent —— 编排决策被收进了对话 Agent 自身。这正是本次重构的核心,见下一页。

07 · 核心重构

从 [READY] 两段式,到标准 function calling

✗ 旧方案 · 两段式

1对话 Agent 在文本里输出 [READY] 魔法标记
2后端正则匹配标记,判断是否就绪
3再调一次独立 orchestrator Agent 决定派哪些子 Agent
✗两次模型调用、标记易误触发、解析脆弱
→

✓ 新方案 · tool_call 单跳

1对话 Agent 直接调用 trigger_generation 工具
2工具参数自带 agents[] · summary · reasoning
3流式 delta.tool_calls 分片累积 + 一次 JSON.parse
✓单次调用 · 决策可审计 · 取消 orchestrator
// 流式 tool_call 分片累积 (conversation-agent.ts)
for (const tc of delta.tool_calls) {
  const slot = toolCalls.get(tc.index) ?? { argsBuffer: "" };
  slot.argsBuffer += tc.function.arguments;  // 累积 JSON 分片
  toolCalls.set(tc.index, slot);
}
// 流结束后一次性解析 → 触发并行生成
const args = JSON.parse(slot.argsBuffer);  yield { type: "tool_call", ...args };

10 · 架构对比

与传统 Agent 架构的区别

核心:混合架构 —— 对话层是 agentic(LLM 自主决定何时/生成什么),生成层是 workflow(确定性并行 fan-out),呼应 Anthropic「Workflow vs Agent」之分。

维度传统 ReAct 自主循环传统 Orchestrator + WorkersCycleMind(本项目)
控制流单 Agent 自主循环,步数不定Planner 规划再派活,多一跳对话 1 次决策 + 确定性并行,无循环
决策位置每轮让模型决定下一步专门 orchestrator agenttool_choice:auto 内嵌对话层,砍掉 orchestrator
子任务执行反复调工具、看结果再决定worker 间需协调来回5 个专家函数,单次生成,互不通信
并发串行(依赖上一步结果)多为串行 / manager 协调Promise.all() 5 个真并行
人类介入多为全自主,不确认通常不确认tool_call → 确认面板 → 用户点确认
可预测性/成本步数 token 不可控,可能空转多跳,较贵步数固定 · token 可控 · 无空转
◆
这是一个明确的工程取舍:该放权的地方放权(需求澄清用 LLM 自主),该确定的地方确定(文档生成用并行 workflow)。
11 · 架构反思

这套架构的优点与缺点

✅ 优点

可预测 · 低成本 · 不空转无自主工具循环,步数固定,token 可控,不会死循环烧钱。
低延迟并行Promise.all() + SSE 完成即回传,墙钟 = 最慢的 Agent。
关注点分离,易迭代6 个职责单一 Agent,可单独调优 / 替换 / 测试。
Human-in-the-loop 闸门确认面板防误判生成,省钱且用户可控。
单跳决策,可审计 + 健壮结构化 tool_call 取代 [READY] 正则;reasoning 存 metadata 可复盘;单 Agent 失败不阻塞其它。

⚠️ 缺点(附应对)

子 Agent 一次性,无自纠错单次 completion,质量有天花板。→ 未来加 critique/verify 回路。
并行文档可能不一致design 与 er 同时生成、看不到对方本轮输出。→ 改半串行或加一致性校对。
上下文粗粒度仅截断旧文档塞进 Prompt,无结构化共享状态。→ 语义合并 / 结构化传递。
任务图固定,不通用只支持 5 类文档,处理不了模板外任务。→ 对本领域是有意取舍。
长会话丢早期上下文历史窗口最近 20 条 × 4k 字符。→ 对话摘要 / RAG 检索补回。
◆
用确定性 workflow 换速度、成本、可复现性,把 LLM 自主性只留在需求澄清环节 —— 缺点已识别,且都有明确演进路线。

15 · 架构亮点

全局生成 Store · 切页面也不中断

⚡
SSE reader 脱离组件生命周期
SSE 读取循环是 Zustand store 里的 fire-and-forget 异步闭包,不依赖任何 React 组件挂载 —— 用户切到别的会话、甚至离开工作台,后台生成照常进行。
🗺
Map<sessionId, Run> 多会话并发
每个会话一条 GenerationRun(状态 / 步骤 / 各 Agent 进度 / 完成文档),多个生成任务互不干扰。
⛔
AbortController 随时取消
每条 Run 持有 AbortController,用户可中途取消;组件重新挂载时直接读 runs.get(sessionId) 续上进度。
// stores/generation-store.ts
interface GenerationRun {
  sessionId: string;
  status: "running"|"completed"|"error";
  streamSteps: StreamStep[];
  agentToolParts: Map<string, AgentPart>;
  completedDocs: string[];
  abortController: AbortController | null;
}
// runs: Map<sessionId, GenerationRun>
// 全局对象 · 跨页面持久 · 独立于 React
